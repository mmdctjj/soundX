## 修复 apps/harmony 通知栏只显示长时任务通知、不显示系统媒体播控卡片
- **根因**：系统媒体播控卡片由 AVSession 驱动，但显示的前提是「系统能把正在发声的音频流和 AVSession 关联」。关联靠 AVPlayer 的 `audioRendererInfo.usage`（StreamUsage）——项目从未设置，音频流不被识别为媒体流，于是通知栏只有 `startBackgroundRunning` 自动挂的"正在运行"普通通知。
- **关键约束**：`audioRendererInfo` 只能在 AVPlayer **initialized 态、首次 prepare 前**设置；切歌走 `reset()` 会回到 idle → 重新 initialized，所以每次进 initialized 都要补设。
- **修复**：
  - `IAudioPlayer.load` 加 `contentType?: string` 参数；`AVPlayerBackend.load` 存到 `currentContentType`，在 stateChange 的 `initialized` 分支设 `audioRendererInfo = { usage: MUSIC→STREAM_USAGE_MUSIC / AUDIOBOOK→STREAM_USAGE_AUDIOBOOK, rendererFlags: 0 }`，再 prepare。
  - `PlayerStore.loadCurrent` 把 `t.contentType ?? this.contentMode` 透传给 `audioBackend.load`。
- 验证：同前，待 DevEco 装 API 22 SDK 后 Sync。

## KEEP_BACKGROUND_RUNNING 是 ACL 受限权限（不是普通敏感权限）
- 用户反馈「AGC 申请相关权限」后定位到：`ohos.permission.KEEP_BACKGROUND_RUNNING` 不是普通敏感权限，而是**受限开放权限（ACL）**——默认普通应用**完全不能用**，必须经 AGC 审核通过才能用。光在 `module.json5` 里声明没用，`backgroundTaskManager.startBackgroundRunning` 会失败（被 try/catch 静默吞掉），导致通知栏只显示"正在运行"普通通知、媒体播控卡片不出现。
- **允许申请的场景**：运动健康、音乐播放、导航、即时通讯（声仓属于音乐/有声书播放，完全符合）。
- **申请路径**：
  - **调试白名单**（推荐先走）：发邮件到 `agconnect@huawei.com`，附 APP ID + 申请权限名 + 使用场景说明。审核周期 1 个工作日。通过后重新生成 Profile（p7b），DevEco Signing Config 重新指定，重新打包 HAP。
  - **正式上架申请**：AGC → 我的应用 → 权限与隐私 → 受限开放权限申请表单 → 新增 KEEP_BACKGROUND_RUNNING → 填使用场景、最大时长、演示视频、用户开关截图等。
- **现状**：`avSessionService.ets:270-290` 的 `startAudioBackgroundTask` 把错误 catch 后只打 `Logger.w`，无法在日志一眼区分是「权限拒绝」还是「其他错误」。建议改 catch 提示文案为「受限权限未开通」。
- **已升级**：把 `startBackgroundRunning` 的 `BackgroundMode.AUDIO_PLAYBACK` 枚举改成 API 18+ 字符串数组 `['audioPlayback']`，并利用返回值 `ContinuousTaskNotification`（含 notificationId / slotType / contentType）打印到日志。功能完全等价，只是 API 风格更新到最新。catch 文案同步改成「检查 AGC 是否已批准 KEEP_BACKGROUND_RUNNING」。

## 论坛帖子的 `continuousTask` API 是假的，勿信
- 论坛帖 https://developer.huawei.com/consumer/cn/forum/topic/0208221751755237219 提到 `import { continuousTask } from '@kit.BackgroundTasksKit'` 后调 `continuousTask.start(...)` 是**更简洁的新 API**。
- **实际**：OpenHarmony 官方 `@kit.BackgroundTasksKit.d.ts` 实际只导出 `backgroundTaskManager`、`bundleState`、`deviceStandby`、`reminderAgent`、`reminderAgentManager`、`usageStatistics`、`workScheduler`、`backgroundProcessManager`、`WorkSchedulerExtensionAbility`、`WorkSchedulerExtensionContext` —— **根本没有 `continuousTask` 这个命名空间**。
- 那个帖子的 `continuousTask` 代码照抄编译都过不了。`backgroundTaskManager.startBackgroundRunning(...)` 才是**唯一正确的官方 API**。
- 论坛帖另错：`session.on('next', ...)` / `session.on('previous', ...)` 事件名错误，正确是 `'playNext'` / `'playPrevious'`（官方文档 arkts-apis-audio-e#streamusage 确认）。
- 论坛帖还缺的：1. `audioRendererInfo.usage = STREAM_USAGE_MUSIC/AUDIOBOOK`（AVPlayer initialized 态设置）；2. `setBackgroundPlayMode(ENABLE_BACKGROUND_PLAY)`（API 24+）；3. `setAVPlaybackState` 播放态下发；4. ACL 权限要在 AGC 申请并通过才能用。

## 参考官方 AudioCast 示例的两点实战改进（`avSessionService.ets`）
- **官方示例**：`gitcode.com/HarmonyOS_Samples/AudioCast`（`AudioRendererController.ets:225, 270`）。用的是 `audio.AudioRenderer`（低层 PCM），架构和我们的 `media.AVPlayer` 不同，**不能照搬**，但有两点实战经验可以参考：
  1. **每次进入播放都要重新申请后台长时任务**。后台长时任务被系统回收超过阈值后会失效，只在 `installAVSessionService` 申请一次不够。我们在 `pushPlaybackState` 里两个分支触发：① 首次播放 `activate` 时同步申请；② `pause→play` 状态翻转时再次申请。
  2. **`wantAgent` 用 `context.abilityInfo.bundleName/name`** 而不是 `context.applicationInfo.name` + 硬编码 abilityName。重构/分包不会断。
- **代码改动汇总**（`apps/harmony/products/entry/src/main/ets/services/avSessionService.ets`）：
  - `startAudioBackgroundTask(context)` → `startAudioBackgroundTask()`（用模块级 `abilityContext`）+ wantAgent 改 `abilityInfo`
  - `bindLaunchWantAgent` wantAgent 同改 `abilityInfo`
  - `pushPlaybackState` 在 `isPlaying && !sessionActivated` 和 `isPlaying && stateFlipped && lastPlaybackState === PAUSE` 两处调 `startAudioBackgroundTask()`
  - 函数幂等：重复调用不抛错（catch 仅 warn）

### 车机模式底部空白 bug（第二次修复）

- **症状**：车机模式右列底部 tab 栏上方、艺人/专辑/合集/播放列表详情页底部仍有一大块空白（约 56vp）。HomeTab 的「调整顺序」按钮上方也明显。
- **根因**：所有页面用 `.padding({ bottom: miniPlayerHasContent() ? 116 : 56 })` 给 GlobalBottomBar+MiniPlayer 占位，但车机模式下：
  - RootShellPage 已隐藏 GlobalBottomBar（之前的修复）
  - MainPage 的 `carContentPanel` 已自带 padding({bottom:56}) 避让车机 tab 栏 → 叠加 HomeTab 自身的 56 = 112，**多 56 空白**
  - 详情页（NavDestination 子页）全屏覆盖，无底部 tab 栏占位 → 仍是 56 空白
- **修复**：6 页面 7 处统一改成 `.padding({ bottom: this.carModeEnabled ? 0 : (miniPlayerHasContent() ? 116 : 56) })`，**车机模式 = 0**。
  - `pages/MainPage.ets:572`（已有 carModeEnabled）
  - `pages/SearchPage.ets:289, 332`（加 StorageLink）
  - `pages/ArtistDetailPage.ets:317`（加 StorageLink）
  - `pages/AlbumDetailPage.ets:293`（加 StorageLink）
  - `pages/CollectionDetailPage.ets:118`（加 StorageLink）
  - `pages/PlaylistDetailPage.ets:184`（加 StorageLink）
- **结论**：车机模式设计核心规则 ——「**tab 栏占位由布局容器自己负责，内容区不能额外加 56**」。下次涉及车机模式新增页面时，paddingBottom 务必用同一个三元公式。
- **编译坑**：ArkTS 不支持跨 struct 自动捕获 `this`，所以同一个文件里如果有多个 `struct`（如 MainPage.ets 有 `HomeTab` 和 `MainPageContent`），每个 struct **必须各自声明** `@StorageLink('carModeEnabled')`。错误信息：「Property 'carModeEnabled' does not exist on type 'HomeTab'」——别以为在同一个文件就共享上下文了。
